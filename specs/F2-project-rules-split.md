## Context

`AGENTS.md` (from `skeleton/AGENTS-template.md`) is meant to be the shared implementor rulebook, but each project
edits it: the "Project-Specific Architecture Boundaries" section is a fill-in placeholder, Coding Rules carries a
`PROJECT-SPECIFIC` marker, and Test Rules 1–3 are written for one stack (`it.skip`, `jest.useFakeTimers`), so
projects on another stack rewrite them (patent-analysis changed them to `pytest.skip` / `uv run pytest`). Once
edited, a project's `AGENTS.md` can no longer be replaced from the skeleton, so every global rule change needs a
manual merge (the "unclear" path in `/upgrade-workflow`).

`PROJECT_AGENT.md` was introduced in v25 as an optional project-owned file, read only if `AGENTS.md` points at it.
No project has one (checked 2026-10-06 across `~/Development/*/`).

**Goal:** all project-owned implementor rules live in one required, project-owned file, `PROJECT_AGENTS.md`.
`AGENTS.md` contains only shared text, so it can be replaced wholesale from the skeleton on every upgrade.

### File roles

| File | Owner | Contents | On upgrade |
|------|-------|----------|-----------|
| `AGENTS.md` | Template | Shared rules only | Replaced from skeleton (backup as `AGENTS.md.bak`) |
| `PROJECT_AGENTS.md` (renamed from `PROJECT_AGENT.md`) | Project | Architecture boundaries, stack-specific coding and test rules, anything else project-specific | Never overwritten |

### Decisions (agreed 2026-10-10)

1. **Name:** `PROJECT_AGENTS.md`, to match `AGENTS.md`. No project has the old name, so no rename migration.
2. **Shared Test Rules:** Rules 4–7 stay shared. For Rules 1–3 the neutral intent ("no skipped tests, no
   sleeps, clean up timers/state") stays shared and the framework specifics (`it.skip`, `jest.useFakeTimers`)
   move to the project file. Check Coding Rules and "Tests Before Reporting" for the same mixing.
3. **Migration:** simple rule. Move only the named project sections; flag reworded shared text for manual review;
   the user approves the proposed files before anything is applied.
4. **Precedence:** `PROJECT_AGENTS.md` wins over `AGENTS.md` on project specifics and may tighten rules, but must
   not weaken the shared safety rules (Review Ledger Protocol, "Checks Are Not Yours To Change"). `AGENTS.md`
   states this.
5. **Missing file:** `./implement` hard-stops with a clear message. `verify-repo` warns in v34, fails from v35.
6. **Scope:** one version (v34), built in three phases (below); `VERSION` is bumped in the last phase only.
7. **Required, created everywhere:** `setup.sh` creates it for new projects; `/upgrade-workflow` creates a stub
   for existing projects that lack one, so the hard stop never blocks a project. The skeleton ships short
   placeholders, so a near-empty file is valid.
8. **Loading:** Codex auto-loads only `AGENTS.md`, so `AGENTS.md` says to read `PROJECT_AGENTS.md` in full first,
   and the `./implement` prompts and the aider and Gemini configs name it.

### Hazard: symlinks make some changes live immediately

Scripts, commands and configs are symlinked into projects, so phase 2 (the hard stop, aider/Gemini loading) is live
in every project the moment it is merged, while their `PROJECT_AGENTS.md` only appears when they run
`/upgrade-workflow` (phase 3). The v34 changelog must say so, as v33's did. Do not merge phase 2 without phase 3's
upgrade step being ready to ship in the same release.

### Not in scope

- Merging the older shared wording in patent-analysis's `AGENTS.md` up to the current skeleton (a side effect of
  the migration, otherwise separate).
- Changing `CODING.md` ownership; it stays project-owned.
- The self-hosting restructure itself (`commands/` holding real files, `in_template_root()`, `tests/test_template.py`)
  is separate work on this branch; F2 builds on it and must not undo it.

## Phase 3 — Migration, changelog and version
<!-- detail: pending -->

### Goal
Existing projects can move to the split safely; ship it as v34.

### Entry criteria
Phases 1 and 2 closed.

### Acceptance Criteria
- `commands/upgrade-workflow.md` gains Step 1b (project version below 34), implementing this migration:
  1. If `PROJECT_AGENTS.md` exists, read it; it is kept and appended to, never overwritten.
  2. Compare the project's `AGENTS.md` with the **v33** `AGENTS-template.md`. Move to `PROJECT_AGENTS.md` only:
     the "Project-Specific Architecture Boundaries" entries; Coding Rules and Test Rules the project added
     beyond the skeleton's; the content of the `PROJECT-SPECIFIC` block.
  3. Flag, but do not move or decide, anything else that differs from the v33 skeleton (reworded shared rules,
     stack substitutions in Test Rules 1–3 such as `pytest.skip` / `uv run pytest`, older shared text from
     skipped versions). List each hunk; the user decides; stack substitutions are typically appended to
     `PROJECT_AGENTS.md`.
  4. If `AGENTS.md` has no customisation, write `PROJECT_AGENTS.md` from the skeleton (placeholders only) with no
     questions. A project with no `PROJECT_AGENTS.md` and nothing to move still gets the stub (decision 7).
  5. Show the proposed `PROJECT_AGENTS.md`, the new skeleton `AGENTS.md` and the flagged hunks; apply only after
     approval.
  6. On approval: save the old `AGENTS.md` as `AGENTS.md.bak` (not committed; stop and ask if one exists), write
     `PROJECT_AGENTS.md`, replace `AGENTS.md` with the skeleton, update the project's own `CLAUDE.md`/`WORKFLOW.md`
     rows.
  After v34, `/upgrade-workflow` treats `AGENTS.md` as "replace from skeleton" with no customisation check and
  never touches `PROJECT_AGENTS.md`. The old "unclear" example about customised `AGENTS.md` boundaries
  (lines ~147–158) is updated to match.
- `CHANGELOG.md` v34 entry (summary; what changed; what projects must do; the symlink hazard from Context;
  "`PROJECT_AGENT.md` (v25, optional) renamed to `PROJECT_AGENTS.md` and made required; no project had one") and
  `VERSION` = 34.
- Verified by dry-run on copies, results pasted into the End-of-Run Report: patent-analysis's `AGENTS.md` (the
  proposed `PROJECT_AGENTS.md` keeps its four boundaries and Test Rules 3–5 content; stack substitutions are
  flagged, not silently moved) and a project with an untouched skeleton `AGENTS.md` (needs no user decision);
  and a later `/upgrade-workflow` leaves `PROJECT_AGENTS.md` untouched.
- `./implement F2.3 --plan` style prompts in a migrated project name both files (manual check).
